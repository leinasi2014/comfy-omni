# ComfyOmni 首期重构与开发目标

本方案是当前唯一架构与开发范围，替代已删除的“离线转换 → 新模型包 → 运行”路线。
[任务 #4](https://github.com/leinasi2014/comfy-omni/issues/4) 维护实时进度和验收证据。
**目标架构不等于功能已经实现。**

## 1. 首期只交付模型运行能力

ComfyOmni 是 vLLM-Omni 插件。首期以 H3 为标准：直接引用已经存在的 ComfyUI 模型与组件文件，
在 RAM/VRAM 中加载、卸载、复用和切换，保留当前已验证的旧 H3 运行路径。

- 一套固定、已有、可用的模型环境反复用于代码回归；模型文件只读挂载。
- 切换模型只改变内存/显存中的驻留及运行状态，不生成另一份完整模型或融合权重。
- 按明确格式加载原始权重；优先用原生表示，必要适配在加载阶段有界内存中完成。
- 实际运行必须使用所选模型，不能静默换权重、精度或组件，也不能只返回成功状态。
- 节点、图执行器、可视化工作流、完整 LoRA 和工具能力排到后续扩展，不作为首期完成门槛。

支持更多 ComfyUI 模型、LoRA、工具与节点仍是长期方向。首期留下稳定扩展边界，不预做这些系统。

## 2. 最小架构与已有能力

| 职责 | 首期工作 | 现有落点 |
|---|---|---|
| 组件来源绑定 | 原路径、组件角色、格式、配置、已验证身份；既有包也只是来源之一 | `artifacts`、`contracts`、组件目录 |
| 格式加载器 | 从原文件输出宿主能消费的张量或量化对象；限制峰值内存 | 共享数值函数、`runtime/h3` |
| 驻留与会话 | 组件级 CPU/GPU 驻留、请求租约、活动模型代次、缓存及预算 | `runtime` |
| 宿主适配 | 把来源加载和装卸接到真实 vLLM-Omni pipeline/worker | `integrations/vllm_omni` |
| 应用入口 | 模型/组件选择、加载、卸载、切换、状态查询 | `application`、现有 API/plugin |

保留单一发行包、轻量插件注册、组件目录与已经验证的 legacy curve-cache 兼容路径。
当前 [H3 来源路由](../src/comfy_omni/integrations/vllm_omni/pipelines/runtime_pipeline.py) 从
`additional_config.comfy_omni_h3` 的 `active` 和 `sources` 选择已登记的原始 ConvRot DiT，
直接建立来源 binding，不经过导出包验证入口；共享组件继续引用已有的宿主可读目录。
固定 A、B 的原文件迭代器分别位于 `runtime/h3/raw_beta4.py` 和 `runtime/h3/raw_standard.py`，
[H3 pipeline](../src/comfy_omni/integrations/vllm_omni/pipelines/beta4_pipeline.py) 将其接入实际宿主
权重加载器，并校验逻辑槽位、形状和执行 dtype。

原始 INT8/ConvRot 字节不能直接冒充 BF16 张量。格式加载器负责必要表示适配和峰值预算，
离线导出器的文件写出部分不能成为运行前置。原文件加载和驻留控制已有小型样本的真实宿主回归；
这些证据不代表固定大模型的完整生成与切换已通过，也不代表任意 ComfyUI 格式均可直接加载。
运行配置和公开 API 见 [H3 原文件运行说明](guides/h3-original-files.md)。

既有导出包及工具源码暂按实际兼容需要保留；错误方向的方案、操作教程和生成架构图直接删除。
不再以“历史路线”保存另一套开发步骤。必要归属留在 [来源记录](migration/source-attribution.md)。

## 3. 加载、卸载、复用、切换

现有 [驻留协调器](../src/comfy_omni/integrations/vllm_omni/residency_control.py) 通过宿主暂停新请求并
排空在途请求，再调用已有 worker 的装卸和切换接口；各 rank 的状态由独立 predicate RPC 核对。
[公开运行时路由](../src/comfy_omni/api/routes/h3_runtime.py) 提供 status、switch、unload、load 和
resume。当前装卸对象是 DiT，TE、VAE、tokenizer 等共享组件保留；这不是全部组件任意装卸的声明。
以下条目仍是首期验收合同，代码接通不替代完整模型与资源回收的实际验证。

1. 配置现有组件路径。首次登记确认强身份与配置，记录来源；后续加载复用记录并检查文件是否变化。
2. 按所选模型和组件计算 RAM/VRAM 预算，确认格式与几何兼容，再进入运行时变更。
3. 需要的组件按需加载；相同且有效的 TE、VAE、tokenizer 等组件共享句柄，不按请求重复创建。
4. 请求持有模型代次和组件租约；仍在使用的权重不得被另一请求卸载或覆盖。
5. 切换时排空旧代次的请求；内存允许时准备新代次，否则先受控卸载非共享组件，再加载新组件。
6. 新代次完整可用后提交选择，使相关缓存失效。失败时撤销半加载状态，保留或从原文件恢复旧状态。
7. 无使用者的组件按预算 offload 或释放；媒体和状态应能证明实际使用了哪一组模型。

兼容 H3 模型的正常 A→B→A 应在同一控制服务和已有工作进程中完成。工作进程重建只能作为
明确报告的故障恢复或宿主限制下的降级，不能充当 ComfyUI 式正常热加载的通过证据。
同时记录控制/工作进程身份、组件复用、模型代次、耗时、峰值内存/显存及回收后的预算。

## 4. 三个小切片与并行分工

| 切片 | 实际代码结果 | 完成证据 |
|---|---|---|
| H1：原文件加载 | 来源契约与格式加载器接通实际宿主，不要求先导出模型 | 固定 H3 资产相关加载与生成通过；旧路径不退化；没有新模型副本 |
| H2：驻留及切换 | 组件共享、租约、预算、装卸、缓存失效与回滚接通实际运行对象 | 同一控制/工作进程 A→B→A，每步生成正确、共享组件复用、失败可恢复、内存回收 |
| H3：回归与交付 | 相关测试、使用配置与状态输出完善，代码通过保护门禁合入 main | 安装/启动、原文件加载、装卸/切换真实场景通过，限制可复现且说明清楚 |

分工只围绕当前可执行小任务，不另建调度服务：

- 来源加载任务：一个智能体负责原文件迭代读取及格式适配，独占明确加载文件和聚焦测试。
- 驻留任务：另一个智能体负责组件生命周期、状态与失败恢复，独占明确状态文件和聚焦测试。
- 集成与验证：主智能体负责真实宿主接入、共享文件、Git/PR、固定环境回归和验收。

先观察一个确实缺失行为的 RED，做最小修改并验证 GREEN，再整理结构。
可复用的代码和证据直接沿用，不为形式重复测试；完成一小片就集成，不囤积大量分支。
报告以本次能运行的行为、失败缺口及下一小片为准；不以文件数、模型体积或主观百分比报进展。

## 5. 验收与成本边界

详见 [固定模型验证基线](testing/model-validation-baseline.md) 和
[Docker 开发规范](development/docker-first.md)。

- CPU 单元与异常场景使用小型样本；项目执行在 Docker 内完成。
- 真实代码回归复用同一套既有只读资产、固定宿主及配置；分支仅隔离代码、进程和小型输出。
- 首次或来源变化时确认完整身份；无关代码修改不触发整套模型再下载、转换、组包或全量哈希。
- 对直接加载、装卸和切换分别验证实际宿主行为；mock 或拒绝所有输入不能证明加载已实现。
- 固定来源存在格式或宿主缺口时修复该边界并用小样本先验证，不能自动制造大模型副本来绕过。
- 核对原文件未改、新增大文件为零；允许有界的日志、测试记录和正常生成媒体。
- 任务结束、失败或取消后清理本任务进程与临时输出，保留用户原文件、可用基线与必要证据。

所有开发 worktree 只放插件 `.worktrees/<task>`；每个文件一个写入者，主智能体串行集成。
未交付 LoRA 原型保留并暂停，首期不继续投入。模型目录不随 worktree 复制。

## 6. 与 ComfyUI 对齐的范围

首期对齐其“已有文件 → 模型对象 → RAM/VRAM 驻留管理”的运行方式：按需装卸、组件复用、
原文件保持不变。ComfyUI 的模型管理实现可作为行为参考，不能把重建模型文件当作热加载。
依据：[官方模型管理源码](https://github.com/Comfy-Org/ComfyUI/blob/master/comfy/model_management.py)。

后续节点扩展可以使用有类型输入输出、依赖图与输入变化驱动的缓存，复用首期组件句柄、租约
和驻留服务；首期不实现图执行器，也不宣称能直接运行任意 ComfyUI workflow 或自定义节点。
依据：[官方节点声明与缓存规则](https://docs.comfy.org/custom-nodes/backend/server_overview)。

首期完成后再定节点、LoRA、工具和其他模型家族的小目标；它们不会反向扩大本期范围。
